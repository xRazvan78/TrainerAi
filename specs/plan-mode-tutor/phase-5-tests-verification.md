# Phase 5: Tests & End-to-End Verification

## Overview

This phase locks in correctness with backend unit/API tests and a full manual end-to-end run that
exercises the complete Plan Mode loop, including the hybrid auto-advance. It also records graph upkeep.
It comes last because it validates the integrated system from Phases 1–4.

## Prerequisites

- Phases 1–4 implemented.
- `docker compose up -d` (pgvector) with the corpus ingested.
- `LLM_API_KEY` (Mistral) configured in `.env`.
- AutoCAD available for the live auto-advance check (the perception path).

## Goals

- Unit tests for plan state transitions and plan-JSON parsing.
- API tests for the plan endpoints and the Plan WS handshake.
- A documented manual end-to-end pass demonstrating chat → plan → auto-advance + manual Next.
- Graph refreshed via `graphify update .`.

## Technical Design

Follow the existing pytest conventions in `trainerAI_backend/tests/` (see `test_command_api.py`,
`test_rag_service.py`, `test_session_state_service.py`). Mock the LLM HTTP layer the same way existing
LLM-touching tests do (no live Mistral calls in unit tests).

### `tests/test_plan_service.py`

- `test_try_advance_matches_and_advances`: build a `Plan` with step 0 `expected_tool="POLYGON"`,
  active; `try_advance(sid, "polygon")` → step 0 `done`, `current_index==1`, step 1 `active`.
- `test_try_advance_no_match_noop`: `try_advance(sid, "LINE")` when current expects `POLYGON` → returns
  `None`, no state change.
- `test_try_advance_null_expected_tool_requires_manual`: step with `expected_tool=None` never
  auto-advances.
- `test_advance_manual_unconditional`: advances regardless of detected tool.
- `test_clear_and_has_active_plan`: `clear` removes state; `has_active_plan` False after all steps done.
- `test_generate_plan_parses_json` (LLM mocked): feed a canned `{"steps":[...]}` → correct `PlanStep`
  list, step 0 active, stored in `_plans`.
- `test_generate_plan_malformed_json_fallback` (LLM mocked): malformed content → non-empty fallback plan
  (per Phase 1 contract), not a crash.

### `tests/test_plan_api.py`

- `test_plan_create_returns_202`: `POST /api/plan/create` → 202 + `{"status":"accepted"}` (background
  task mocked or DB/LLM mocked).
- `test_plan_advance_ok` / `test_plan_clear_ok`: 200 + expected status.
- `test_plan_ws_accepts_connection`: using FastAPI `TestClient.websocket_connect`, connect to
  `/api/plan/ws/{sid}` and assert it accepts (and optionally receives a `ping`).
- `test_perception_with_active_plan_auto_advances` (integration-lite): seed a plan in `plan_service`,
  POST a perception state whose detected tool matches the current step's `expected_tool`, assert the
  plan advanced and reactive guidance was **not** triggered (mock `guidance_trigger_service` /
  pipeline to assert it wasn't called).

## Testing & Validation

### Automated

```powershell
cd trainerAI_backend
pytest tests/test_plan_service.py tests/test_plan_api.py -v
pytest tests/                     # full suite must stay green
```

Acceptance: new tests pass; no pre-existing tests regress.

### Manual end-to-end

1. `docker compose up -d`
2. `cd trainerAI_backend; uvicorn app.main:app --reload`
3. `cd trainerAI_overlay; cargo tauri dev`
4. In the overlay: click **Plan**, type "draw a hexagon", **Send**.
   - ✅ Checklist populates with ordered steps; each shows an `expected_tool`.
   - ✅ Plan summary appears in the chat transcript.
5. Type "remind me what POLYGON does", **Send**.
   - ✅ Assistant reply streams token-by-token; ends cleanly.
6. In AutoCAD, start the command of step 1 (e.g. `POLYGON`).
   - ✅ Step 1 flips to done ✓, step 2 becomes active ▸ automatically (perception auto-advance).
   - ✅ No reactive guidance pops up while the plan is active.
7. Click **Next**.
   - ✅ The current step advances manually.
8. Click **Close Plan**.
   - ✅ Panel hides; backend plan cleared; reactive guidance resumes on the next tool change.

### Plan-quality spot check (do this right after Phase 2, before UI polish)

Run `/api/plan/create` for 3–4 goals (e.g. "hexagon", "simple rectangular room with a door",
"a bolt") and read the steps. If plans are vague or hallucinate commands, the fix is **corpus
ingestion** (more/better training videos via `app/training/ingest.py`), not code — see README risk note.

## Edge Cases & Risks

- **Flaky LLM JSON** in live runs → covered by `generate_plan_json` fallback; the manual run may
  occasionally show a thin plan — rerun or improve corpus.
- **Perception tool-name format drift** → if auto-advance doesn't fire for an obvious match, log the raw
  `active_tool` vs `expected_tool` and confirm `_normalize_tool` covers the case; consider an alias map
  as a follow-up (out of scope for v1).
- **WS not connected during a test** → API tests should drive the WS via `TestClient.websocket_connect`
  rather than relying on background broadcasts landing anywhere.

## Notes

- After this phase, the full vision is shippable: reactive guidance (unchanged) + goal-driven Plan Mode
